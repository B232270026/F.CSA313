## 2. Лабораторийн зорилго

Энэ лабораторийн зорилго нь эдгээр хэмжүүрийг k6 хэрэгслээр БОДИТООР хэмжиж, ачаалал өсөхөд гүйцэтгэл хэрхэн өөрчлөгддөгийг өөрийн нүдээр харахад оршино.


Туршилтад зөвшөөрөгдсөн public test target болох: https://test.k6.io  ашиглана.

Энэ лабораторийн хүрээнд baseline тест, 5/30/100 VU-ийн тусдаа load test, stages test болон threshold-ийн PASS, FAIL тестүүдийг хийсэн.

VU буюу Virtual User нь тухайн системтэй зэрэгцээ харилцаж байгаа виртуал хэрэглэгчийг илэрхийлнэ. VU-ийн тоог нэмэгдүүлэх замаар системд очих зэрэгцээ request-ийн ачааллыг нэмэгдүүлж, системийн response time болон throughput хэрхэн өөрчлөгдөж байгааг ажигласан.

Гурван туршилтыг ижил endpoint дээр, тус бүр 1 минутын хугацаатай ажиллуулсан. Ингэснээр туршилтын үндсэн нөхцөл ижил бөгөөд зөвхөн VU-ийн тоо өөр байна.

Туршилтын үед дараах дөрвөн үндсэн хэмжүүрийг авч үзсэн.

p90 — request-үүдийн 90% нь энэ хугацаанаас бага хугацаанд хариу авсан гэсэн үг.
p95 — request-үүдийн 95% нь энэ хугацаанаас бага хугацаанд хариу авсан гэсэн үг.
Throughput — нэгж хугацаанд хэдэн HTTP request боловсруулж байгааг харуулна.
Error rate — нийт HTTP request-ийн хэдэн хувь нь алдаатай байсныг харуулна.

### Үр дүнгийн тайлбар дүгнэлт

5 VU-ийн шинэ baseline туршилтаар p95 latency 321.04 ms, throughput 7.210176 req/s, error rate 0% гарсан.

30 VU үед p95 latency 278.77 ms болж, throughput 43.946765 req/s хүртэл нэмэгдсэн.

100 VU үед p95 latency 243.10 ms, throughput 150.148379 req/s, error rate 0% байсан.

Гурван түвшний туршилтын үр дүнгээс харахад VU-ийн тоо 5 → 30 → 100 болж нэмэгдэхэд throughput мэдэгдэхүйц өссөн байна. 5 VU үед throughput 7.210176 req/s байсан бол 30 VU үед 43.946765 req/s, 100 VU үед 150.148379 req/s болж өссөн. Энэ нь ачаалал нэмэгдэхэд тухайн туршилтын нөхцөлд систем илүү олон request боловсруулж байсныг харуулж байна.

Өөрөөр хэлбэл энэ туршилтын үр дүнд VU нэмэгдэхэд p90 болон p95 өсөөгүй, харин буурсан байна. Тиймээс “ачаалал өсөх тусам response time заавал нэмэгдэнэ” гэж энэ туршилтаас дүгнэж болохгүй.

Энэ нь зөвхөн p95-ийг харахаас гадна maximum болон бусад percentile үзүүлэлтүүдийг хамтад нь авч үзэх шаардлагатайг харуулж байна. 5 VU үед maximum response time 470.89 ms, 30 VU үед 892.28 ms, 100 VU үед 1.49 s болсон. Энэ нь өндөр ачааллын үед зарим request бусдаасаа харьцангуй удаан хариу авсан буюу latency spike гарсан байж болохыг харуулж байна. Гэхдээ эдгээр maximum утга нь нийт request-ийн зөвхөн хамгийн удаан request-ийг илэрхийлдэг тул системийн нийтлэг response time-ийг дүгнэхдээ p90, p95 зэрэг percentile үзүүлэлтүүдийг хамтад нь авч үзэх нь илүү тохиромжтой.

Энэхүү үр дүнгээр throughput, response time, percentile, error rate зэрэг performance testing-ийн үндсэн хэмжүүрүүдийг бодитоор хэмжиж, өөр өөр ачааллын үед системийн зан төлөвийг харьцуулсан.

## 8. Threshold Test

### 8.1 PASS
| Metric            | Threshold |    Actual | Result |
| ----------------- | --------: | --------: | ------ |
| p95 response time |  < 437 ms | 274.35 ms | PASS   |
| HTTP error rate   |      < 1% |     0.00% | PASS   |

### 8.2 Intentional FAIL
| Metric            | Threshold |    Actual | Result |
| ----------------- | --------: | --------: | ------ |
| p95 response time |  < 150 ms | 288.74 ms | FAIL   |
| HTTP error rate   |      < 1% |     0.00% | PASS   |

Threshold FAIL болсон нь HTTP request заавал алдаатай болсон гэсэн үг биш. Энэ тохиолдолд request-үүд бүгд амжилттай байсан боловч response time-ийн p(95) нь тохируулсан performance threshold-ээс давсан учраас threshold FAIL болсон.

### SLO-г тодорхойлсон нь

Алхам 2-т хийсэн baseline тестийн үр дүнгээр `p(95)` response time нь **291.27 ms** байсан. Лабораторийн зааврын дагуу baseline-ийн `p(95)` утгыг 1.5 дахин өсгөж SLO-г тодорхойлсон.

Baseline p(95) = 291.27 ms

SLO = 291.27 × 1.5
    = 436.905 ms
    ≈ 437 ms

### Threshold утгуудын сонголт

PASS тестийн `p(95)<437` threshold нь baseline тестийн бодит үр дүнгээс тооцоолсон SLO юм. Baseline тестийн `p(95)` нь 291.27 ms байсан үүнээс тооцож SLO-г 437 ms болгон сонгосон.

FAIL тестийн `p(95)<150` threshold нь системийн бодит SLO биш бөгөөд threshold-ийн FAIL нөхцөлийг зориудаар шалгах зорилгоор сонгосон хатуу босго юм. Туршилтаар `p(95)=288.74 ms` гарсан тул 150 ms-ийн босгыг давж, threshold FAIL болсон.

## 10. Дүгнэлт

Энэхүү лабораторийн ажлаар Grafana k6 ашиглан системийн гүйцэтгэлийг өөр өөр ачааллын түвшинд бодитоор хэмжиж, response time, p90, p95, throughput болон error rate үзүүлэлтүүдийг харьцуулан судаллаа. 5, 30 болон 100 VU-ийн тусдаа туршилтаар VU-ийн тоо нэмэгдэхэд throughput 7.210176 req/s-ээс 43.946765 req/s, цаашлаад 150.148379 req/s болж мэдэгдэхүйц өссөн байна. Харин p95 response time нь 5 VU үед 321.04 ms, 30 VU үед 278.77 ms, 100 VU үед 243.10 ms байсан бөгөөд энэ туршилтын нөхцөлд VU нэмэгдэхэд p95 өсөөгүй, харин буурсан үр дүн гарсан. Иймээс зөвхөн энэхүү туршилтын үр дүнд үндэслэн ачаалал нэмэгдэх тусам response time заавал нэмэгддэг гэж дүгнэж болохгүй. Гэсэн хэдий ч maximum response time 470.89 ms-ээс 892.28 ms, цаашлаад 1.49 секунд болж өссөн нь өндөр ачааллын үед зарим request дээр latency spike гарч болохыг харуулсан. Бүх ачааллын түвшинд HTTP error rate 0.00% байсан тул туршилтын явцад request-ийн алдаа илрээгүй. Мөн baseline тестийн p95 болох 291.27 ms утгыг ашиглан лабораторийн зааврын дагуу SLO-г 437 ms болгон тодорхойлж, threshold PASS тестээр p95 274.35 ms гарч SLO-г хангасныг шалгасан. Үүний зэрэгцээ 150 ms гэсэн зориуд хатуу threshold ашиглан FAIL нөхцөлийг үүсгэж, бодит p95 288.74 ms гарснаар performance threshold хэрхэн зөрчигддөгийг туршиж үзсэн. Stages тестээр ачааллыг 5-100 VU хүртэл үе шаттайгаар нэмэгдүүлж, нийт 2 минут 30 секундын хугацаанд системийн гүйцэтгэлийг ажигласан бөгөөд error rate 0.00% байсан. Эдгээр туршилтаар performance testing-ийн үндсэн хэмжүүрүүдийг бодит туршилтаар хэмжиж, өөр өөр ачааллын үед системийн зан төлөвийг харьцуулахын зэрэгцээ threshold болон SLO-г ашиглан гүйцэтгэлийг үнэлэх практик ойлголт авсан. Гэхдээ энэхүү туршилт нь тодорхой хугацаа, test target болон тухайн үеийн network/server нөхцөлд хийгдсэн тул 100 VU-ийг системийн дээд хүчин чадал гэж үзэх боломжгүй бөгөөд илүү урт хугацаа болон илүү өндөр ачааллын түвшинд нэмэлт туршилт хийх шаардлагатай.
