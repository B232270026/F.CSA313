## 2. Лабораторийн ажлын зорилго

Энэхүү лабораторийн ажлын зорилго нь Reading List Web App системд exploratory testing буюу судлан шинжлэх тестлэлт хийх, тестийн аяллуудыг charter-ийн дагуу төлөвлөх, системийн ажиллагааг бодитоор турших, илэрсэн согогуудыг баримтжуулах, UI болон API түвшний нотолгоо цуглуулахад оршино.

Тестлэлт хийх явцад шаардлагатай талбаруудын баталгаажуулалт, номын оны зөвшөөрөгдөх хүрээ, давхардсан өгөгдөл, хайлтын ажиллагаа болон API-ийн буруу хүсэлтийн боловсруулалтыг шалгасан.

## 4. Тестлэлийн арга зүй

Энэ лабораторид Session-Based Test Management (SBTM) аргачлалд тулгуурласан exploratory testing ашигласан.

Тестлэлт нь дараах үндсэн үе шаттай:

1. **Charter боловсруулах:** Шалгах зорилго, хүрээ, тестийн аяллуудыг тодорхойлох.
2. **Тестийн session явуулах:** Төлөвлөсөн аяллуудын дагуу системийг бодитоор турших.
3. **Нотолгоо цуглуулах:** Screenshot болон API хүсэлтийн бүтэн гаралтыг хадгалах.
4. **Согог баримтжуулах:** Давтан гаргах алхам, хүлээгдэж байсан үр дүн, бодит үр дүн, ноцтой байдлыг тодорхой бичих.
5. **Debrief хийх:** Тестлэлтээс сурсан зүйл, илрээгүй эрсдэл, дараагийн session-д шалгах асуудлыг дүгнэх.

## 5. Тестийн charter ба аяллууд

Тестийн зорилгыг тодорхойлсон `charter.md` файлд үндсэн зорилго болон тестийн аяллуудыг тусгасан.

### 5.1. Аялал 1 — Шаардлагатай талбаруудын баталгаажуулалт

**Зорилго:** Ном нэмэх үед шаардлагатай талбаруудыг систем зөв шалгаж байгаа эсэхийг турших.

Шалгасан нөхцөлүүд:

- Гарчиг хоосон үед ном нэмэх.
- Зохиогч хоосон үед ном нэмэх.
- Он хоосон үед ном нэмэх.
- Амжилттай эсэх мэдэгдэл болон жагсаалтын өөрчлөлтийг шалгах, хайлтын үр дүн гэх мэт нөхцлүүдийг шалгасан.


### 5.2. Аялал 2 — Оны хязгаар ба өгөгдлийн төрөл

**Зорилго:** Номын он зөвшөөрөгдсөн хүрээнд, бүхэл тоон утгатай байгаа эсэхийг шалгах.

Шалгасан утгууд:

- `999`
- `2101`
- `1999.3`

**Үр дүн:** Эдгээр утгыг оруулахад ном нэмэгдсэн. Энэ нь он 1000–2100 хүртэлх бүхэл тоо байх ёстой гэсэн шаардлагатай зөрчилдөж байна.

### 5.3. Аялал 3 — Давхардсан өгөгдөл

**Зорилго:** Ижил гарчиг, зохиогчтой номыг давхар бүртгэх боломжтой эсэхийг шалгах.

**Үр дүн:** Ижил мэдээлэлтэй номыг хоёр удаа нэмэхэд жагсаалтад хоёр мөр үүссэн.

### 5.4. Аялал 4 — Хайлтын ажиллагаа

**Зорилго:** Номын гарчиг болон зохиогчоор хайх үед хайлтын үр дүн зөв гарч байгаа эсэх, том/жижиг үсгийн ялгаа үр дүнд нөлөөлж байгаа эсэхийг шалгах.

**Үр дүн:** Зарим хайлтын оролтоор үр дүн харагдаагүй. Гэхдээ том, жижиг үсгийн ялгаа нь шалтгаан мөн эсэхийг батлахын тулд ижил өгөгдөл дээр харьцуулсан туршилт шаардлагатай.

## 7. API түвшний туршилт

API-ийн буруу JSON хүсэлт боловсруулах ажиллагааг `curl -i` командаар шалгасан.

Ашигласан команд:

```bash
curl -i -X POST http://localhost:3000/api/books \
  -H 'Content-Type: application/json' \
  --data '{invalid-json'
```

### Хүлээгдэж байсан үр дүн

Буруу JSON форматтай хүсэлтийг сервер татгалзаж, `400 Bad Request` статус буцаах ёстой.

### Бодит үр дүн

Туршилтын үед сервер дараах хариу буцаасан:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

Response body:

```json
{"result":"OK"}
```

Энэ нь буруу форматтай JSON хүсэлтийг амжилттай хүсэлт мэт боловсруулсан шинж юм. Бүтэн `curl -i` гаралтыг `evidence/bug-05-curl.txt` файлд хадгалсан.

## 9. Тестлэлтээс гарсан үр дүн

Тестлэлтээр шаардлагатай талбаруудын баталгаажуулалт, оны зөвшөөрөгдөх утга, давхардсан бүртгэл болон API-ийн буруу хүсэлтийн боловсруулалттай холбоотой асуудлууд илэрсэн. Мөн хайлтын ажиллагааг нэмэлтээр шалгах шаардлага гарсан.

Эдгээр үр дүн нь зөвхөн UI-г харахаас гадна хэрэглэгчийн оруулсан өгөгдөл серверт хэрхэн боловсруулагдаж байгааг шалгах хэрэгтэйг харуулж байна.

## 10. Хэсэг E: Дүгнэлт (Debrief)

1. Шаардлагатай талбаруудын баталгаажуулалтын аялал үр дүнтэй байсан бөгөөд гарчиг, зохиогч эсвэл он хоосон байхад ном нэмэгдэж байгааг bug-01 тайланд тэмдэглэсэн.
2. Оны хязгаар болон өгөгдлийн төрлийг шалгах аяллаар `999`, `2101`, `1999.3` утгуудыг зөвшөөрч байгааг bug-02 тайланд баримтжуулсан.
3. Давхардсан өгөгдөл шалгах аяллаар ижил мэдээлэлтэй номыг хоёр удаа бүртгэх боломжтойг bug-03 тайланд тэмдэглэсэн.
4. API-ийн оролтын баталгаажуулалтыг шалгах үед буруу JSON хүсэлтэд `200 OK` буцаж байгааг илрүүлж, бүтэн гаралтыг `evidence/bug-05-curl.txt` файлд хадгалсан.
5. Хайлтын аяллаар зарим хайлтын утгаар үр дүн харагдаагүй боловч том, жижиг үсгийн ялгаа шалтгаан мөн эсэхийг харьцуулсан туршилтаар баталгаажуулах шаардлагатай.
6. Charter-аас гадуур дараагийн удаа шалгаж болох асуудалд устгах үйлдлийн дараах жагсаалтын шинэчлэлт, нийт номын тоолуур, холбоосууд болон хэт урт текстийн харагдац багтана.
7. Дараагийн session-д хайлтын case-insensitive ажиллагаа, устгах үйлдэл, номын тоолуур болон урт текстийн UI харагдацыг шалгах charter сонгоно.
8. Лаб 1-ийн Playwright автомат тестэд хоосон талбар, оны хязгаар, бутархай он, давхардсан ном болон буруу JSON хүсэлтийн шалгалтуудыг бичсэн бол эдгээр согогийг автомат аргаар илрүүлэх боломжтой байсан.
9. Харин хэт урт текстийн харагдац, хэрэглэгчид харагдах мэдэгдлийн ойлгомжтой байдал зэрэг нь автомат тестээр шалгаж болох ч хүний нүдээр ажиглах нь нэмэлт ач холбогдолтой.

## 11. Дүгнэлт

Энэхүү лабораторийн ажлаар Reading List Web App системд exploratory testing хийж, тодорхойлсон тестийн аяллуудын дагуу өгөгдөл оруулах, хайх, давхардал үүсгэх болон API-ийн буруу хүсэлтийг шалгасан. Илэрсэн асуудлуудыг дахин гаргах алхам, хүлээгдэж байсан болон бодит үр дүн, нотолгоотой нь баримтжуулах нь системийн чанарыг үнэлэхэд чухал болохыг ойлгосон. Цаашид автомат тестийн хамрах хүрээг нэмэгдүүлэх, API-ийн алдааны боловсруулалтыг шалгах, UI-ийн ашиглахад ойлгомжтой байдлыг сайжруулах шаардлагатай.
