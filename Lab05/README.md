## 3. Ажлын зорилго

Энэ ажлын хүрээнд оюутныг тодорхой хичээлд бүртгэх REST API-ийн ажиллагааг янз бүрийн оролтын нөхцөлөөр шалгав. Зөвхөн амжилттай бүртгэлийг баталгаажуулах бус, оюутан байхгүй, идэвхгүй, хичээл олдохгүй, урьдач нөхцөл хангагдаагүй зэрэг алдааны нөхцөлүүдийг тус тусад нь туршсан.

Тестийн тохиолдлуудыг тодорхойлохдоо оролтын сонголт, эквивалент анги, төлөөлөх утга болон хүлээгдэх үр дүнг харгалзан үзсэн. Postman-д бэлтгэсэн Collection-ийг Newman-аар ажиллуулж, зөв oracle, зориуд буруу oracle болон серверт холбогдох боломжгүй үеийн үр дүнг харьцуулсан.

## 4. API-ийн бүтэц ба ажиллах зарчим

Тестлэх API нь оюутан, хичээл болон бүртгэлийн мэдээлэлтэй ажиллана. Тестүүдэд шаардлагатай оюутан, хичээлийн мэдээллийг үүсгэхдээ `PUT` хүсэлт ашиглаж, бүртгэлийн үйлдлийг `POST` хүсэлтээр шалгасан.

| Метод | Endpoint | Зориулалт |
|---|---|---|
| PUT | `/students/:id` | Оюутны мэдээлэл үүсгэх эсвэл шинэчлэх |
| PUT | `/courses/:id` | Хичээлийн мэдээлэл үүсгэх эсвэл шинэчлэх |
| GET | `/courses/:id` | Хичээлийн мэдээлэл авах |
| GET | `/registrations` | Бүртгэлийн жагсаалт авах |
| POST | `/registrations` | Оюутныг хичээлд бүртгэх |

### 4.1. Оюутны өгөгдөл бэлтгэх

Оюутны төлөв болон үзсэн хичээлүүдийг `PUT /students/:id` хүсэлтээр тохируулна.

## 6. Тестийн спецификаци

Дараах хүснэгтэд үндсэн тестийн тохиолдлууд болон тэдгээрийн хүлээгдэх үр дүнг тодорхойлов. Статус болон `result` утгыг API-ийн зааварт үндэслэн сонгосон.

| ID | Тестийн нөхцөл | Хүлээгдэх статус | Хүлээгдэх result |
|---|---|---:|---|
| TC01 | Идэвхтэй оюутан, урьдач нөхцөл хангасан | 201 | `OK` |
| TC02 | Оюутан байхгүй | 200 | `ERROR_NO_STUDENT` |
| TC03 | Оюутан идэвхгүй | 200 | `ERROR_INACTIVE_STUDENT` |
| TC04 | Хичээл байхгүй | 200 | `ERROR_NO_COURSE` |
| TC05 | Урьдач нөхцөл дутуу | 200 | `ERROR_PREREQUISITES` |
| TC06 | Хичээл урьдач нөхцөлгүй, оюутан идэвхтэй | 201 | `OK` |
| TC07 | Оюутан болон хичээл хоёулаа байхгүй | 200 | Бодит шалгалтаар тогтооно |
| TC08 | `studentID` талбар дутуу | 400 | `ERROR_BAD_REQUEST` |
| TC09 | `courseID` талбар дутуу | 400 | `ERROR_BAD_REQUEST` |
| TC10 | Буруу JSON формат | 400 | `ERROR_BAD_JSON` |

TC07 нь давхар алдааны туршилт юм. Оюутан болон хичээл хоёулаа байхгүй үед сервер аль нөхцөлийг түрүүлж шалгаж байгааг бодит хариу болон `server.js`-ийн кодтой харьцуулан тэмдэглэнэ.

TC05 дээр зөвхөн алдааны нэрийг шалгахгүй. `missing` массивт шаардлагатай хичээлийн код орсон эсэхийг мөн баталгаажуулна.

## 7. Тест бүрийн бие даасан байдал

Тестийн үр дүнг өмнөх тестийн ажиллуулалтаас хамааралгүй байлгахын тулд тухайн тохиолдолд шаардлагатай өгөгдлийг өөрийн setup хүсэлтээр бэлтгэнэ.

Жишээлбэл:

- **TC01:** Идэвхтэй оюутан болон урьдач нөхцөлтэй хичээлийг PUT хүсэлтээр үүсгэнэ.
- **TC02:** Хичээлийг үүсгэж, оюутны setup-ийг зориудаар хийхгүй.
- **TC03:** Оюутныг `inactive` төлөвтэй үүсгэж, хичээлийг бэлтгэнэ.
- **TC04:** Оюутныг үүсгэж, байхгүй хичээлийн код ашиглана.
- **TC05:** Оюутны `coursesTaken`-ийг хоосон байлгаж, `CS201` шаардсан хичээл үүсгэнэ.
- **TC07:** Оюутан болон хичээлийн setup хоёуланг хийхгүй.

Энэ зохион байгуулалт нь тестүүдийг дангаар нь ажиллуулах, Collection-ийг давтан ажиллуулах үед өмнө хадгалагдсан өгөгдлөөс үүсэх хамаарлыг багасгана.

## 8. Oracle буюу хүлээгдэх үр дүнгийн шалгалт

Тест бүрийн үр дүнг үнэлэхдээ дараах төрлийн assertion ашиглана:

1. HTTP статус код хүлээгдэж буй утгатай таарч байгаа эсэх.
2. JSON response-ийн `result` талбар зөв утгатай эсэх.
3. Амжилттай бүртгэлд `registrationID` байгаа эсэх.
4. `registrationID` нь тоон төрөлтэй эсэх.
5. Урьдач нөхцөл дутсан үед `missing` массив шаардлагатай кодыг агуулж байгаа эсэх.

Жишээ oracle:

```javascript
// 1. Статус код 201 (Created) эсэхийг шалгах
pm.test("Status code is 201", function () {
  pm.response.to.have.status(201);
});

// 2. Хариултын (Response) result нь "OK" байгааг шалгах (Oracle)
pm.test("Result is OK", function () {
  const body = pm.response.json();
  pm.expect(body.result).to.eql("OK");
});

// 3. Dynamic ID-г шалгах зөв арга (Oracle)
// ID (hardcoded) 1 байна гэж шалгаж болохгүй.
// Харин ID нь хоосон биш, тоон утга эсвэл оршин байгааг шалгана:
pm.test("Registration ID exists and is valid", function () {
  const body = pm.response.json();
  pm.expect(body).to.have.property("registrationID");
  pm.expect(body.registrationID).to.be.a("number"); // эсвэл > 0
});
```

Эдгээр шалгалтыг зөвхөн амжилттай бүртгэл хүлээгдэж буй хүсэлтэд хэрэглэнэ. Алдааны тохиолдол бүр өөрийн хүлээгдэх `result` утгатай байна.

## 9. Давхар алдааны хослолын туршилт

Нэг хүсэлтэд хоёр алдаа зэрэг үүсэх үед серверийн хариуг урьдчилан таамаглахын оронд туршилтаар тодорхойлов. Энэ тохиолдолд оюутан болон хичээлийн мэдээллийг хоёуланг нь үүсгэхгүй.

**Хүсэлт:**

```json
{
  "studentID": "B231234574",
  "courseID": "CS998"
}
```

- Оюутны бичлэг байхгүй.
- Хичээлийн бичлэг байхгүй.
- Серверийн бодит статус: `200 OK`
- Серверийн бодит `result`: `ERROR_NO_STUDENT`

**Ажиглалт, дүгнэлт:**

Туршилтын үр дүнд оюутан болон хичээлийн мэдээлэл хоёулаа байхгүй үед сервер `ERROR_NO_STUDENT` хариу буцаасан. Энэ нь тухайн хүсэлтийг боловсруулах үед оюутны мэдээллийг шалгах нөхцөл хичээлийн мэдээллийг шалгах нөхцөлөөс түрүүлж шалгагдаж байгааг харуулж байна.

Иймээс давхар алдааны хослолын туршилтаар серверийн алдаа боловсруулах дарааллыг бодит хариунд тулгуурлан ажиглав.

| Connection error | `ECONNREFUSED 127.0.0.1:3000` |

Энэ туршилтаар API сервер ажиллахгүй байсан тул нийт 20 хүсэлт бүгд холболтын алдаатай дууссан. Newman-ийн тайланд HTTP статус код шалгах болон JSON хариу унших шалгалтууд мөн амжилтгүй болсон. Учир нь серверээс бодит HTTP хариу ирээгүй бөгөөд JSON хариуг унших боломжгүй байсан.

`ECONNREFUSED` алдаа нь API серверийн хаяг, порт руу холболт тогтоож чадаагүйг илэрхийлнэ. Энэ нь зориуд буруу болгосон oracle-оос үүдсэн алдаанаас ялгаатай. Иймээс DOWN туршилтын үр дүнгээр сервер ажиллахгүй үеийн холболтын алдааг таньж, Newman ажиллуулалт амжилтгүй болсныг `exit=1` кодоор илэрхийлж байгааг ажиглав.
## 12. Newman үр дүнгийн файлууд

Ажиллуулалтын гурван үр дүнг `results/` хавтаст тус тусад нь хадгалсан.

```text
results/
├── newman-pass.txt
├── newman-fail.txt
└── newman-down.txt
```

| Файл | Зорилго | Баталгаажуулах зүйл                  |
|---|---|--------------------------------------|
| `newman-pass.txt` | Зөв oracle бүхий ажиллуулалт | Failed assertions 0, exit code 0     |
| `newman-fail.txt` | Нэг oracle зориуд буруу | Failed assertions 1, exit code 1     |
| `newman-down.txt` | Сервер унтарсан үе | ECONNREFUSED болон бодит exit code 1 |

README-д оруулсан assertion-ы тоо, алдааны тоо болон exit code нь эдгээр файлын бодит гаралттай ижил байна.

## 15. Илэрсэн согог ба ажиглалт

Туршилтын явцад API-ийн амжилттай болон алдаатай нөхцөл дэх хариу, мөн сервер ажиллахгүй үеийн Newman-ийн төлөвийг ажиглав.

| Туршилт | Хүлээгдсэн зан төлөв | Бодит ажиглалт | Дүгнэлт |
|---|---|---|---|
| TC01 — Амжилттай бүртгэл | HTTP 201, `result: OK` хариу буцаах | HTTP 201 Created хариу буцсан | Амжилттай бүртгэлийн хариу хүлээлттэй нийцсэн. |
| TC07 — Оюутан ба хичээл байхгүй | Тодорхойлсон алдааны хариу буцаах | HTTP 200, `ERROR_NO_STUDENT` буцсан | Оюутан олдоогүй алдаа түрүүлж буцаж байгааг ажигласан. |
| FAIL — Буруу хүлээлттэй тест | TC01-ийн статусыг зориудаар HTTP 200 гэж шалгах | Бодит статус HTTP 201 байсан тул нэг assertion амжилтгүй болсон | Newman буруу хүлээлтийг илрүүлсэн. Энэ нь зориудаар өөрчилсөн тестийн хүлээлтийн алдаа болохоос API-ийн согог гэдгийг дангаар нотлохгүй. |
| DOWN — Сервер ажиллахгүй | Сервертэй холбогдож чадахгүй үед алдааг мэдээлэх | `ECONNREFUSED 127.0.0.1:3000`, 20 хүсэлт амжилтгүй, exit code 1 | Сервер ажиллахгүй үед Newman холболтын алдааг мэдээлж, ажиллуулалт амжилтгүй болсныг илэрхийлсэн. |
## 16. Git хувилбарын удирдлага

Ажлын явцад Git ашиглан төслийн өөрчлөлтүүдийг үе шаттай бүртгэсэн. Commit history нь орчин бэлтгэсэн, тестийн спецификаци боловсруулсан, Collection үүсгэсэн, Newman үр дүн хадгалсан болон тайлан эцэслэсэн ажлуудыг тусгасан.

## 17. Дүгнэлт

Энэ лабораторийн ажлаар REST API-ийн бүртгэлийн үйлдлийг олон төрлийн оролтын нөхцөлөөр шалгах тестийн багц боловсруулсан. Эхлээд API-ийн үндсэн ажиллагааг судалж, дараа нь оюутан, хичээл болон урьдач нөхцөлийн төлөвүүдийг тус тусад нь ангилсан. Төлөөлөх утгуудыг сонгохдоо зөвхөн амжилттай бүртгэлээс гадна алдаа үүсгэх нөхцөлүүдийг хамруулсан. Тест бүрт шаардлагатай setup хүсэлтийг оруулснаар өмнөх тестийн үүсгэсэн өгөгдлөөс хамаарах байдлыг багасгасан.

Хамгийн их анхаарал шаардсан хэсэг нь Postman дээр тестийн хүсэлт, хүлээгдэж буй хариу болон assertion-уудыг зөв тохируулах, мөн PASS, FAIL, DOWN туршилтуудыг тусад нь ажиллуулж үр дүнг хадгалах байсан. Давхар алдааны хослолоор оюутан болон хичээл хоёулаа байхгүй үед HTTP 200 статус кодтой `ERROR_NO_STUDENT` хариу буцаж, оюутны алдааг түрүүлж шалгаж байгааг ажигласан. Newman-ийн PASS, FAIL болон DOWN ажиллуулалтуудыг тусдаа текст файлд хадгалсан.

Зориуд буруу болгосон oracle-ийн үр дүнгээр автомат тест хүлээгдсэн үр дүнгээс зөрсөн тохиолдлыг илрүүлэх боломжийг шалгасан. Туршилтын явцад API-ийн согогийг баттай тогтоогоогүй боловч тестийн хүлээлтийн зөрүү болон сервер ажиллахгүй үеийн холболтын алдааг илрүүлсэн. Мөн оюутан байхгүй үед тухайн оюутны үзсэн хичээлийг шалгах, хичээл байхгүй үед урьдач нөхцөлийг шалгах зэрэг утгын хувьд боломжгүй хослолыг тусад нь авч үзэх шаардлагатайг ойлгосон.

Эцэст нь тестийн үр дүнг тайлантай тулгаж, API-г системтэй тестлэхэд бие даасан тест, зөв oracle болон давтагдахуйц туршилт чухал болохыг ойлгосон.
