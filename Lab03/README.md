## 5. Тестлэх локал API-гаа босгох  

Энэхүү лабораторийн туршилтыг хийхийн тулд Node.js болон Express ашиглан локал API сервер үүсгэсэн. API сервер нь `localhost:3000` дээр ажиллах бөгөөд дараагийн k6 тестүүдэд performance, reliability болон availability шинжүүдийг шалгах зорилгоор гурван endpoint ашигласан.

API-ийн үндсэн бүтэц:

| Method | Endpoint    | Зориулалт                     |
| ------ | ----------- | ----------------------------- |
| POST   | `/cart/add` | Сагсанд бараа нэмэх           |
| GET    | `/report`   | Тайлангийн мэдээлэл авах      |
| POST   | `/pay`      | Төлбөрийн хүсэлт боловсруулах |

## 5.1 `/cart/add`

`/cart/add` endpoint нь хэрэглэгч сагсанд бараа нэмэх үйлдлийг төлөөлнө. Энэ endpoint-д зориудаар нэмэлт delay болон failure оруулаагүй бөгөөд амжилттай хүсэлтэд `HTTP 200` хариу буцаана.

```json
{
  "ok": true,
  "items": 1
}
```

Энэ endpoint-ийг **Performance scenario**-д ашигласан. Учир нь нэмэлт delay байхгүй тул хэвийн ачааллын үед response time-ийг хэмжихэд тохиромжтой.

## 5.2 `/report`

`/report` endpoint нь тайлан боловсруулах үйлдлийг төлөөлнө. Performance тестийн үед response time тодорхой хэмжээнд удаан байх нөхцөлийг бий болгохын тулд 200–400 ms-ын санамсаргүй delay оруулсан.

```js
await sleep(200 + Math.random() * 200);
```

Амжилттай хүсэлтийн үед:

```json
{
  "rows": 20000
}
```

гэсэн response буцаана.

Энэ endpoint-ийг нэмэлт **Performance scenario**-д ашиглаж, response latency-ийн `p95` утгыг хэмжинэ.

## 4.3 `/pay`

`/pay` endpoint нь хэрэглэгчийн төлбөр хийх үйлдлийг төлөөлнө. Reliability scenario-д системийн failure rate-ийг хэмжихийн тулд хүсэлтийн ойролцоогоор 5%-д `HTTP 500` алдаа буцаахаар тохируулсан.

```js
if (Math.random() < 0.05) {
  return res.status(500).json({
    error: 'gateway timeout'
  });
}
```

Алдаа гараагүй тохиолдолд төлбөр амжилттай болсон тухай response буцаана.

Энэхүү зориудаар үүсгэсэн failure нь `/pay` endpoint-ийн **error rate**-ийг k6 ашиглан хэмжих боломжийг бүрдүүлсэн. Reliability scenario-ийн SLO-д уг error rate-ийг ашиглана.

## 7. SLO тодорхойлолт

Сценарио бүрийн хэмжүүрийг Service Level Indicator (SLI) болгон авч, тухайн системийн шаардлагатай түвшинг Service Level Objective (SLO) хэлбэрээр тодорхойлсон.

| Сценарио     | SLI                          | SLO босго        | Цонх / нөхцөл                        |
| ------------ | ---------------------------- | ---------------- | ------------------------------------ |
| Performance  | `/cart/add` response latency | **p95 < 50 ms**  | 20 VU тогтмол ачаалал, 1 минут       |
| Reliability  | `/pay` error rate            | **< 8%**         | 20 VU, 1 минут                       |
| Availability | Нийт хүсэлтийн success rate  | **≥ 90%**        | 20 VU, 2 минут, 10 секундийн зогсолт |
| Supporting Performance | `/report` p95 latency  | **p95 < 450 ms**        | 20 VU, 1 минут |


### 7.1 Performance SLO

`/cart/add` endpoint-ийн response time-ийн 95 дахь percentile буюу `p95` нь **50 ms-ээс бага** байх шаардлагатай гэж үзсэн.

**Босго сонгосон шалтгаан:** `/cart/add` endpoint дээр зориудаар нэмэлт delay оруулаагүй тул хэвийн 20 VU ачааллын үед хэрэглэгчийн хүсэлт хурдан боловсруулагдах шаардлагатай гэж үзэн 50 ms-ийн босгыг сонгосон.

### 7.2 Reliability SLO

`/pay` endpoint-ийн error rate **8%-иас бага** байна.

**Босго сонгосон шалтгаан:** `/pay` endpoint дээр ойролцоогоор 5%-ийн failure probability зориудаар оруулсан тул туршилтын санамсаргүй хэлбэлзлийг тооцож, түүнээс бага зэрэг өндөр буюу 8%-ийг SLO-ийн босго болгон сонгосон.

### 7.3 Availability SLO

2 минутын туршилтын хугацаанд нийт хүсэлтийн **дор хаяж 90% нь амжилттай** байх шаардлагатай.

**Босго сонгосон шалтгаан:** туршилтын явцад серверийг зориудаар 10 секунд зогсоож, дахин ажиллуулах тул богино хугацааны тасалдлыг зөвшөөрсөн боловч нийт системийн availability 90%-иас доош орохгүй байхаар босго тогтоосон.

### 7.4 Availability Error Budget

Availability SLO нь **90%** байгаа тул 2 минутын туршилтын цонхонд зөвшөөрөгдөх downtime буюу error budget:

```text
2 минут × (1 - 0.90)
= 2 × 60 × 0.10
= 12 секунд
```

Иймээс энэхүү SLO-ийн дагуу 2 минутын хугацаанд **12 секунд хүртэлх хугацааг availability-ийн error budget** гэж үзэж болно.

Гэхдээ k6 дээр availability-г хүсэлтийн амжилтын хувиар хэмжих тул дараагийн chaos туршилтаар хүсэлтийн тоонд суурилсан availability-г мөн тооцно. Сервер 10 секунд зогссон хугацаанд хэдэн хүсэлт амжилтгүй болсноос шалтгаалан хүсэлтээр тооцсон үр дүн нь 12 секундын хугацааны error budget-тэй яг адил гарахгүй байж болно.

###7.5 Supporting Performance SLO — /report

/report endpoint-ийн response time-ийн p95 нь 450 ms-ээс бага байх шаардлагатай гэж үзсэн.

Босго сонгосон шалтгаан: /report endpoint дээр 200–400 ms-ийн зориудаар үүсгэсэн delay байгаа тул уг endpoint-ийн үндсэн delay-ийн хүрээнд ажиллахын зэрэгцээ бага хэмжээний хэлбэлзлийг зөвшөөрөх зорилгоор 450 ms-ийн босгыг сонгосон.

PASS туршилтын үед /report endpoint-ийн бодит p95 нь 390.58 ms байсан. Энэ нь 450 ms-ийн SLO босгоос бага тул тухайн туршилтын үед /report endpoint-ийн Performance SLO хангагдсан.

### Detailed Results

Туршилтын хугацаанд нийт **929 iteration**, **2787 HTTP request** гүйцэтгэсэн. Нийт HTTP request-ийн 49 нь амжилтгүй болсон бөгөөд энэ нь нийт request-ийн **1.75%** байна.

`/pay` endpoint-ийн хувьд 929 хүсэлтээс 49 нь амжилтгүй болсон тул тухайн endpoint-ийн error rate **5.27%** байв. Энэ нь уг endpoint дээр зориудаар оруулсан ойролцоогоор 5%-ийн failure probability-тэй нийцэж, сонгосон **<8%** reliability SLO-г хангаж байна.

`/cart/add` endpoint-ийн p95 latency **2.46 ms** байсан нь **50 ms**-ийн threshold-ээс бага байна. Харин `/report` endpoint-ийн p95 latency **390.58 ms** байсан бөгөөд **450 ms**-ийн threshold-ийг мөн хангаж байна.

Нийт checks-ийн амжилтын хувь **98.24%** байсан нь availability-д тодорхойлсон **90%-ийн** босгоос өндөр байна.
